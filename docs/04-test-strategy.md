# 04. AI Agent 테스트 전략

> LLM이 낀 시스템은 "실행할 때마다 답이 다르다"는 이유로 테스트를 포기하기 쉽습니다.
> 이 프로젝트는 **결정적으로 검증 가능한 것**과 **통계적으로 평가해야 하는 것**을
> 구분하는 전략을 취합니다.

## 1. 테스트 피라미드

```
          ┌──────────────────────┐
          │  품질 평가 (Eval)     │  ← 로드맵 (§5): 실제 LLM, 통계적 평가
          ├──────────────────────┤
          │  API 통합 테스트      │  8건 — FastAPI TestClient + MockLLM
          ├──────────────────────┤
          │  에이전트 루프 테스트  │  7건 — MockLLM 시나리오 재생
          ├──────────────────────┤
          │  단위 테스트          │ 23건 — 데이터/ML/도구
          └──────────────────────┘
                 총 38건, 전부 오프라인 (API 키·네트워크 불필요, ~6초)
```

핵심 원칙: **결정적인 부분(도구, 루프, API 계약)은 CI에서 매번 검증하고,
비결정적인 부분(LLM의 도구 선택·문장 품질)은 Eval로 분리한다.**

## 2. MockLLM — 에이전트 루프를 결정적으로 만들기

에이전트 루프의 정합성(도구 실행, 결과 전달 형식, 오류 처리, 반복 상한)은
LLM의 지능과 무관한 **프로토콜 문제**입니다. 따라서 LLM을 스크립트로 대체합니다.

```python
llm = MockLLM([
    make_tool_use_response([("t1", "analyze_survival", {"group_by": "Sex"})]),
    make_final_response("여성 생존율은 74.2%입니다."),
])
agent = TitanicAgent(llm, executor)   # 도구는 실제로 실행됨 (수치는 진짜 데이터)
```

- `LLMClient`가 Protocol 인터페이스라 프로덕션 코드 수정 없이 교체 가능
- Mock은 호출 인자까지 기록(`llm.calls`)해 "도구 결과가 올바른 형식의 tool_result로
  되돌아갔는가"를 턴 단위로 검증
- 도구 실행은 Mock이 아니라 **실제 실행** — LLM만 빼고 전부 진짜

## 3. 계층별 검증 항목

| 계층 | 파일 | 대표 검증 |
|---|---|---|
| 데이터 | `test_data.py` | 891행 로드, 파생 피처, 알려진 생존율(38.38%)·결측(177) 일치 |
| ML | `test_ml.py` | CV 정확도 > 75%(다수결 기준선 61.6% 대비), 확률 범위, **방향성**(1등석 여성 > 3등석 남성), 결측 운임 처리 |
| 도구 | `test_tools.py` | 실측치 회귀(여성 74.2%), 필터 결합, 화이트리스트 위반 거부, 문자열 수치 보정, 빈 결과 처리 |
| 에이전트 루프 | `test_agent.py` | 도구 호출→결과 반영→최종 응답 흐름, **병렬 호출 결과의 단일 턴 반환**, 오류의 is_error 변환, max_turns 안전 종료, 멀티턴 이력 |
| API | `test_api.py` | 계약(스키마·상태 코드), 유효성 422, LLM 미설정 503, 세션 404, MockLLM 주입 E2E |

설계 포인트:

- **실측치 회귀 테스트** — "여성 생존율 74.2%" 같은 알려진 값을 상수로 박아,
  전처리 변경이 분석 결과를 조용히 바꾸는 사고를 방지
- **방향성 테스트** — ML은 정확도 수치보다 도메인 지식과의 부합(여성/상위 등급 우대)을
  함께 검증해야 파이프라인 버그(라벨 뒤집힘 등)를 잡을 수 있음
- **오류 경로 우선** — 화이트리스트 위반, 빈 필터 결과, 알 수 없는 도구, 세션 소멸 등
  LLM이 실수할 수 있는 입력을 도구 계층에서 전부 흡수하는지 확인
- **리뷰 발견 → 회귀 테스트화** — 다관점 코드 리뷰에서 확인된 결함(스키마 위반 filters로 인한
  크래시, `!=` 필터의 결측 포함, 단일 행 std의 NaN JSON, max_tokens로 잘린 tool_use의
  세션 손상 등)은 수정과 함께 반드시 재현 테스트를 남겨 재발을 차단

## 4. 실제 LLM 연동 검증 (수동 스모크)

배포 전 수동 체크리스트 — 비용이 들고 비결정적이므로 CI에서 제외:

```bash
python scripts/demo.py "성별 생존율을 비교해줘"          # 도구 1회 호출 + 수치 인용 확인
python scripts/demo.py "30세 여성이 1등석이었다면?"      # predict_survival 선택 확인
python scripts/demo.py "선장 이름이 뭐야?"               # 범위 밖 질문 거부 확인
```

## 5. 로드맵: 품질 평가(Eval) 자동화

CI 테스트가 "루프가 규약대로 도는가"를 보장한다면, Eval은 "에이전트가 **잘** 답하는가"를
측정합니다. 다음 단계로 설계해 둔 방안:

| 지표 | 측정 방법 | 판정 |
|---|---|---|
| 도구 선택 정확도 | 골든 질문 30개에 기대 도구를 라벨링, 실제 호출과 비교 | 자동 (기계 판정) |
| 수치 인용 정확도 | 답변에서 수치를 추출해 도구 반환값과 대조 | 자동 |
| 범위 밖 질문 거부율 | 답변 불가 질문 10개에 대한 거부 응답 여부 | LLM-as-judge |
| 답변 품질 | 명료성·근거 제시 루브릭 채점 | LLM-as-judge |

- 실행 비용 관리: PR마다가 아니라 프롬프트/모델 변경 시에만 실행
- 회귀 기준: 이전 릴리스 점수 대비 하락 시 병합 차단
