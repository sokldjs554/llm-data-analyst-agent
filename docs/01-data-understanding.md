# 01. 대상 업무·데이터의 이해와 분석

> AI Agent 개발의 첫 단계는 "무엇을 물어볼 수 있는 데이터인가"를 정확히 아는 것입니다.
> 이 문서는 대상 데이터셋을 분석하고, 그 결과가 에이전트 설계(도구·프롬프트·ML)에
> 어떻게 반영되었는지를 정리합니다.

## 1. 업무 시나리오 정의

가상의 업무 요구사항을 다음과 같이 설정했습니다.

> "사내 구성원이 SQL이나 pandas를 몰라도, 자연어로 승객 데이터에 대해 질문하고
> 근거 수치가 포함된 답을 받을 수 있어야 한다. 기존 시스템은 생존 예측 결과만
> API로 받아 쓸 수 있어야 한다."

이 요구에서 도출한 기능 요건:

| 요건 | 대응 |
|---|---|
| 자연어 질의 → 근거 기반 답변 | AI Agent (`/chat`) |
| 집계·비교·조건부 분석 | 분석 도구 3종 (overview, analyze_survival, get_statistics) |
| 가정형 질문("~라면 생존했을까?") | ML 예측 도구 (predict_survival) |
| 시스템 간 연계 (LLM 불필요) | 독립 ML API (`/predict`) |

## 2. 데이터셋 개요

- **출처**: 타이타닉 승객 명단 (Kaggle 학습용 표본, 891명)
- **목적 변수**: `Survived` (0=사망, 1=생존) — 전체 생존율 **38.4%**

| 컬럼 | 타입 | 결측 | 설명 |
|---|---|---|---|
| Pclass | int | 0 | 객실 등급 (1/2/3) — 사회경제적 지위의 대리 변수 |
| Sex | str | 0 | 성별 |
| Age | float | **177 (19.9%)** | 나이 |
| SibSp / Parch | int | 0 | 동반 형제·배우자 / 부모·자녀 수 |
| Fare | float | 0 | 운임 (편중 심함: 3등석 중앙값 8.05 vs 1등석 60.3) |
| Cabin | str | **687 (77.1%)** | 선실 번호 |
| Embarked | str | 2 | 탑승 항구 (S/C/Q) |

### 파생 피처

| 피처 | 정의 | 근거 |
|---|---|---|
| `Familysize` | SibSp + Parch | 동반 가족 규모가 생존과 비선형 관계 (아래 §3) |
| `AgeGroup` | 나이 구간화 (0-16/17-26/27-36/37-62/63+) | 연령대별 생존 패턴 분석용, EDA 노트북의 구간을 계승 |

## 3. 핵심 패턴 (에이전트가 답할 수 있어야 하는 사실들)

실데이터 기준 검증된 수치 — 테스트(`tests/test_tools.py`)에서 회귀 검증합니다.

**성별 — 가장 강한 단일 요인**

| 성별 | 인원 | 생존율 |
|---|---|---|
| 여성 | 314 | **74.2%** |
| 남성 | 577 | **18.9%** |

**객실 등급 — 뚜렷한 계층 효과**

| 등급 | 인원 | 생존율 |
|---|---|---|
| 1등석 | 216 | 63.0% |
| 2등석 | 184 | 47.3% |
| 3등석 | 491 | 24.2% |

**그 외 주요 패턴**

- 어린이(0-16세) 생존율 55.0% > 전체 평균 38.4% — "여성과 아이 먼저" 구조와 일치
- 탑승 항구 C(셰르부르) 55.4% vs S(사우샘프턴) 33.7% — 항구 자체가 아니라
  **C 항구에 1등석 승객 비율이 높은 교란 효과**로 해석해야 함 (에이전트 프롬프트에서
  단순 상관을 인과로 단정하지 않도록 지시하는 근거)
- 가족 동반 1~3명일 때 생존율 최고(55~72%), 혼자(30.4%)이거나 대가족(16.1%)이면 급락 —
  `Familysize` 피처를 만든 이유

## 4. 데이터 품질 이슈와 대응 전략

| 이슈 | 분석 | 대응 |
|---|---|---|
| Age 결측 19.9% | 결측이 무작위가 아닐 수 있음 (3등석에 결측 집중) | ML: 파이프라인 내 중앙값 대치(SimpleImputer)로 학습/추론 일관성 보장. 분석 도구: 결측 제외 후 집계하고 count를 함께 반환해 표본 크기를 투명하게 노출 |
| Cabin 결측 77.1% | 대치가 무의미한 수준 | ML 피처와 에이전트 조회 대상에서 제외 (`QUERYABLE_COLUMNS` 화이트리스트) |
| Fare 편중 | 최댓값 512로 극단값 존재 | StandardScaler로 스케일링, 도구는 중앙값·사분위수를 함께 제공 |
| 표본의 대표성 | 1912년 침몰 사고 표본 891명 | 시스템 프롬프트에 "데이터 범위를 벗어난 일반화 주의" 지시 |

## 5. EDA 노트북 → 프로덕션 모듈 개선 내역

출발점인 `notebooks/titanic-eda.ipynb`(Kaggle 노트북)의 자산을 어떻게 발전시켰는지가
이 프로젝트의 서사입니다.

| 노트북 (before) | 모듈 (after) | 개선 효과 |
|---|---|---|
| 셀 단위 수동 `fillna(mean)` | `SimpleImputer(median)` 를 파이프라인에 내장 | 학습·추론 시점 동일 변환 보장, 중앙값으로 극단값 영향 감소 |
| 수동 라벨 인코딩 (`SexNum`, `EmbarkedNum`) | `OneHotEncoder(handle_unknown="ignore")` | 미지의 범주 입력에도 안전 |
| `SVC()` 단독 학습, 검증 없음 | `CalibratedClassifierCV(SVC)` + 5-fold CV | **CV 정확도 82.7%**, 보정된 확률 출력 (예측 API의 확률 신뢰도 확보) |
| 일회성 셀 실행 | `data.py`/`ml.py` 모듈 + 테스트 | 에이전트·API가 재사용, 회귀 검증 가능 |

## 6. 이 분석이 에이전트 설계로 이어진 지점

1. **컬럼 화이트리스트** (`QUERYABLE_COLUMNS`) — Cabin처럼 품질이 낮은 컬럼,
   Name/PassengerId처럼 개인 식별성이 있는 컬럼은 도구에서 제외
2. **도구가 count를 항상 반환** — 필터링 후 표본이 작아지는 문제를 LLM이 인지하고
   답변에 반영하도록 설계
3. **시스템 프롬프트의 주의 문구** — 교란 효과(§3 탑승 항구)와 표본 한계(§4)를
   근거로, 수치 인용·과잉 일반화 금지 지시를 명문화
