# 02. AI Agent 개발 전략

> 요구사항에서 출발해 아키텍처·도구·모델·프롬프트를 어떤 근거로 선택했는지,
> 그리고 무엇을 의도적으로 하지 않았는지를 기록합니다.

## 1. 문제 정의와 접근 수준 선택

LLM 활용에는 난이도 스펙트럼이 있습니다: **단일 호출 → 워크플로 → 에이전트**.
무조건 에이전트가 정답이 아니므로, 먼저 요구사항이 에이전트 수준을 필요로 하는지 검토했습니다.

| 판단 기준 | 이 프로젝트의 답 |
|---|---|
| 사전에 단계를 고정할 수 있는가? | ✗ — "성별과 등급을 비교해줘" 같은 질문은 필요한 도구 조합이 질문마다 다름 |
| 중간 결과에 따라 다음 행동이 달라지는가? | ✓ — 필터 결과가 비어 있으면 조건을 바꿔 재시도해야 함 |
| 오류를 복구할 수 있는가? | ✓ — 도구 오류를 LLM에 되돌려 스스로 정정 (is_error 패턴) |

→ **모델 주도(tool-use) 에이전트**가 적합. 단, 반복 상한(`max_turns`)으로 폭주를 통제.

## 2. 아키텍처: 수동 루프를 선택한 이유

SDK가 제공하는 자동화된 tool runner 대신 **수동 tool-use 루프**(`agent.py`)를 구현했습니다.

| 고려 사항 | 수동 루프의 이점 |
|---|---|
| 관측 가능성 | 모든 도구 호출을 `ToolCallRecord`로 남겨 API 응답·감사 로그에 노출 |
| 테스트 용이성 | LLM 인터페이스(`LLMClient` Protocol)만 Mock으로 교체하면 루프 전체를 오프라인 검증 |
| 제어 지점 | 반복 상한, 오류→is_error 변환, stop_reason별 분기(refusal/pause_turn)를 명시적으로 처리 |
| 학습 곡선 | 에이전트 동작 원리가 코드에 그대로 드러나 유지보수자가 블랙박스 없이 이해 가능 |

트레이드오프: 루프 코드를 직접 유지해야 하지만, 약 60줄 수준으로 부담이 작습니다.
프로덕션에서 스트리밍·압축(compaction) 요구가 커지면 SDK tool runner로의 전환을 재평가합니다.

핵심 구현 규칙 (Claude tool-use 규약 준수):

- 병렬 도구 호출 결과는 **하나의 user 턴**에 모든 `tool_result`를 모아 반환
  (분리하면 모델이 병렬 호출을 학습적으로 회피하게 됨)
- 어시스턴트 턴은 제공자가 반환한 **원본 콘텐츠 블록 그대로** 이력에 보존
  (`raw_content` — thinking 블록 보존 요구사항 대응)
- 도구 실패는 예외 전파가 아니라 `is_error: true` 결과로 변환 → LLM이 스스로 정정

## 3. 도구 설계: 안전성 우선

**원칙: LLM에게 임의 코드 실행 권한을 주지 않는다.**

"pandas 코드를 생성해 exec()로 실행"하는 접근은 유연하지만, 프롬프트 인젝션 한 번이면
파일 시스템 접근·데이터 유출로 이어질 수 있습니다. 대신 다음과 같이 설계했습니다.

| 설계 | 내용 | 효과 |
|---|---|---|
| 구조화 질의 | 필터를 `{column, op, value}` 목록으로만 수용 | 표현식 파싱·코드 실행 자체가 없음 |
| 화이트리스트 | 컬럼(`QUERYABLE_COLUMNS`)·연산자(`ALLOWED_OPS`) 허용 목록 검증 | 인젝션이 성공해도 피해 범위 = "허용된 조회" |
| 입력 방어 | 수치형 컬럼에 문자열 값이 오면 변환 시도, 실패 시 명확한 오류 | LLM의 타입 실수를 흡수 |
| 오류 메시지 설계 | "허용 컬럼 목록"을 오류에 포함 | LLM이 재시도 시 스스로 정정 가능 |

도구는 4개로 최소화했습니다 (도구가 많을수록 선택 오류율이 올라감):

| 도구 | 역할 | 대응 질문 예 |
|---|---|---|
| `get_dataset_overview` | 스키마·결측·기본 통계 | "이 데이터에 뭐가 있어?" |
| `analyze_survival` | 그룹별 생존율 (+필터) | "등급별 생존율은?" |
| `get_statistics` | 컬럼 통계/빈도 (+필터) | "1등석 평균 나이는?" |
| `predict_survival` | ML 가정 시나리오 예측 | "30세 여성이 1등석이었다면?" |

각 도구 description에는 **언제 호출해야 하는지**(트리거 조건)를 명시했습니다 —
"무엇을 하는 도구인지"만 쓰면 모델의 도구 선택 정확도가 떨어지기 때문입니다.

## 4. 모델·프롬프트 전략

- **모델**: `claude-opus-4-8` (기본값, 환경 변수로 교체 가능). 도구 선택 정확도와
  한국어 품질 기준으로 선정. 적응형 사고(`thinking: adaptive`)를 켜 복잡한 비교 질문에서
  추론 품질을 확보.
- **시스템 프롬프트 핵심 규칙** (`agent.py`):
  1. 수치는 반드시 도구 결과에서 인용 — 환각 억제
  2. 데이터로 확인 불가한 질문은 그렇다고 답변 — 범위 밖 질문 거부
  3. 표본 한계(891명, 1912년)를 벗어난 일반화에 주의 문구 — 데이터 이해 문서 §4의 반영
- **프롬프트-도구 역할 분리**: "어떻게 분석할지"는 프롬프트가 아니라 도구 스키마가
  구조로 강제합니다. 프롬프트는 스타일과 인용 규칙만 담당해 취약성을 줄입니다.

## 5. 시스템 연계 전략

에이전트를 "모 아니면 도"로 도입하게 하지 않는 것이 핵심입니다.

```
연계 시스템 A (챗봇)      → POST /api/v1/chat     (LLM 필요)
연계 시스템 B (백오피스)  → POST /api/v1/predict  (LLM 불필요)
연계 시스템 C (대시보드)  → GET  /api/v1/dataset/summary (LLM 불필요)
```

- LLM 미설정 시 `/chat`만 503을 반환하고 나머지는 정상 동작 — **장애 격리**
- 세션 기반 멀티턴(`session_id`)으로 챗봇 연계 시 대화 맥락 유지
- 상세: [03-api-spec.md](03-api-spec.md)

## 6. 하지 않은 것 (의도적 범위 제한)

| 항목 | 이유 |
|---|---|
| RAG / 벡터 DB | 현재 데이터는 정형 데이터 — 검색이 아니라 집계가 필요. 문서 데이터가 추가되는 시점의 로드맵 항목 |
| LangChain 등 프레임워크 | 도구 4개 규모에서는 추상화 비용 > 이득. 직접 구현이 동작 원리 증명에도 유리 |
| 대화 이력 영속화 | 인메모리 + 상한(100세션)으로 시작, 프로덕션 전환 시 Redis 교체 지점만 명시 |
| 스트리밍 응답 | 데모 범위에서는 단순 응답으로 충분. FastAPI SSE로 확장 가능 |

## 7. 확장 로드맵

1. **품질 평가(Eval) 자동화** — 골든 질문 30개에 대해 도구 선택 정확도·수치 인용
   정확도를 측정하는 회귀 스위트 ([테스트 전략 §5](04-test-strategy.md))
2. **스트리밍 + 이력 영속화** — SSE 스트리밍, Redis 세션 저장소
3. **도구 확장** — 시각화 생성(차트 이미지 반환), 사용자 데이터셋 업로드
4. **멀티 데이터셋 일반화** — 도구 계층을 데이터셋 어댑터로 추상화해
   임의 정형 데이터에 같은 에이전트를 재사용
